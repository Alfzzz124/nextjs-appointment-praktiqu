# Can `openapi.yaml` be generated automatically?

**Date:** 2026-07-27
**Short answer: yes — and it is worth doing, but it is not a one-command drop-in.**

---

## 1. First, a correction about which file is which

There are two specs in this repo and they describe different APIs:

| File | Size | What it actually is |
|---|---|---|
| `openapi.yaml` (root) | 350 KB | The **KiviCare WordPress plugin** API — generated by static analysis of `register_rest_route()` calls. Not ours. |
| `docs/api/openapi.yaml` | 211 KB, 187 paths | **Ours** — the Next.js `/api/v1` surface. |

`docs/api/openapi.yaml` says "generated from route files" in its header, but **no generator
script exists anywhere in the repo**. It was produced once and has been hand-maintained
since. That is precisely why it drifts, and why the cuid→numeric ID change would
otherwise have to be applied by hand across 187 paths.

## 2. What was tested

I trialled [`next-openapi-gen`](https://github.com/tazo90/next-openapi-gen) (v1.7.0)
against a real route from this codebase — `src/app/api/v1/clients/route.ts` plus its
`validation.ts`.

**Without annotations** it discovered the route and both methods automatically, but
produced empty schemas:

```json
"/v1/clients": { "get": { "responses": { "200": { "schema": {} } } } }
```

**With JSDoc annotations** on the handler:

```ts
/**
 * Register a client
 * @description Creates a WordPress user with the kiviCare_patient capability.
 * @body createClientSchema
 * @response ClientDetailResponse
 * @auth bearer
 * @tag Clients
 */
export async function POST(req: NextRequest) { … }
```

…it resolved the real Zod schema into real fields:

```
summary   : Register a client
security  : [{'BearerAuth': []}]
tags      : ['Clients']
bodyRef   : #/components/schemas/createClientSchema
properties: ['fullName','email','mobileNumber','dateOfBirth','gender','address',
             'emergencyContact','notes']
```

The config that made Zod resolution work (this took two attempts — `schemaDir` pointing
at `./src` produced empty components):

```json
{
  "apiDir": "./src/app/api",
  "schemaDir": "./src/services",
  "schemaType": "zod",
  "outputFile": "openapi.yaml"
}
```

## 3. What it costs

- **Route discovery and HTTP methods: free.** No annotation needed.
- **Request bodies, query params, responses, auth, tags: one JSDoc block per handler.**
  187 routes, of which 95 already import a Zod schema — those are quick, the remaining
  92 need their shapes described.
- Response schemas need named types the generator can resolve; today most handlers
  return `NextResponse.json(...)` with an inline shape, so response types would have to
  be extracted into named exports.

Realistically: **~1.5–2 days** to annotate the whole surface, done incrementally
route-group by route-group. Not a single command.

## 4. ⚠️ Why it is not installed yet

`next-openapi-gen@1.7.0` depends on `typescript: npm:@typescript/typescript6@6.0.2` —
it pulls a **second TypeScript major** into the tree alongside our 5.9.3. npm also
resolves plain `npm i -D next-openapi-gen` to **0.10.5** here, not 1.7.0, presumably a
peer constraint against Next 14.

Adding a dependency that ships its own TypeScript major is a real risk to the build, and
not a call to make silently in the middle of a data-layer migration. **The dependency
was deliberately reverted.** The research stands; adopting it is a decision to take
explicitly.

## 5. Alternatives if that dependency is unacceptable

| Option | Trade-off |
|---|---|
| [`@asteasolutions/zod-to-openapi`](https://github.com/asteasolutions/zod-to-openapi) | No TS-major conflict. You register schemas and paths in code, so the spec is built explicitly rather than discovered — more control, more boilerplate, and route discovery is manual. |
| [`next-openapi-route-handler`](https://github.com/omermecitoglu/next-openapi-route-handler) | Type-safe wrapper around each handler; the spec falls out of the wrapper. Cleanest long-term, but it means rewriting all 187 handlers to the wrapper form. |
| A small in-repo generator | Full control, no new dependency; but it is a parser to write and maintain, and the existing hand-maintained file is the evidence that unowned tooling rots. |

**Recommendation:** `next-openapi-gen`, pinned, *if* the second TypeScript in the tree
proves harmless in a scratch install (test `npm run build` and `tsc --noEmit` before
committing the lockfile). Otherwise `@asteasolutions/zod-to-openapi`, which has no such
conflict and reuses the Zod schemas already written.

## 6. Immediate consequence for the ID break

Until a generator is wired up, `docs/api/openapi.yaml` still documents client ids as
cuid strings. That is now wrong — they are numeric `wp_users.ID` (decision D2). The
paths needing correction are `/api/v1/clients*`, and the Laravel front-end and Postman
collection must move with them in the same release.
